# scratchllm

A bilingual (Arabic/English) GPT built from scratch in PyTorch: data pipeline, tokenizer, model,
training, generation and evaluation, engineered as a tested, reproducible package. It is a
learning project (following Raschka's *Build a Large Language Model From Scratch*) that is also
meant to be engineered properly: every component has tests that define its contract, every
non-obvious choice is recorded with its evidence in [docs/DECISIONS.md](docs/DECISIONS.md), and
numbers are generated by commands, not typed.

> **Status.** The pipeline from raw web text to a trained, evaluated and sampled model works end
> to end on one 4 GiB GPU. The 17M-parameter model has been trained for 5,000 steps (164M tokens,
> about one epoch of the data): it writes fluent-looking Arabic and English with local sense but no
> coherent meaning over several sentences, and greedy decoding loops. Its loss falls as expected for
> its size and budget; the checks that looked for a fault found none (D-023). Cutting English from
> 39% to 20% of the training tokens improved Arabic and cost English (D-024). RMSNorm, rotary embeddings
> and SwiGLU are built as options; together they scored lower bits per character than the GPT-2 parts on the trained languages in two seeds, though not on the Moroccan Wikipedia, which was never trained on (D-027 to D-029). A key/value cache for generation exists (D-030). Not built yet:
> LoRA/SFT, grouped-query attention (see [docs/PROBLEM.md](docs/PROBLEM.md)). Full status and evidence:
> [docs/DECISIONS.md](docs/DECISIONS.md) (entries D-001 to D-033).

## Results so far

| What | Result | Source of the number |
|---|---|---|
| Tokenizer fertility, Arabic (tokens per word, 16,384 ids) | **1.78** against 5.51 for the GPT-2 tokenizer and 2.39 for Qwen3 (151k ids) | `reports/tokenizer/final-v2` |
| Tokenizer fertility, English | 1.78 against 1.32 (GPT-2) and 1.31 (Qwen3): worse than both | same |
| 17.1M-parameter model after 164M tokens (5,000 steps), bits per character on held-out Arabic (5 trained sources, mean of validation) | **2.02**, 0.58 of what a model knowing only the token frequencies of Arabic reaches (D-026) (a uniform guess costs 4.15). After the 49M-token pilot: 2.42 | `reports/eval/final-local-17m`, `reports/eval/final-pilot-17m`, `reports/eval/final-d026-unigram` |
| Same, on 3 dialects never seen in training | **2.75** (pilot: 3.28) | same |
| Same, English (FineWeb-Edu) | **1.56** (pilot: 1.91) | same |
| Same model trained with English at 20% of the tokens instead of 39% (one seed): Arabic val / unseen dialects / English | **1.97** / **2.73** / **1.63**, against 2.02 / 2.75 / 1.56 for the row above | `reports/eval/final-ablation-english-20-long`, D-024 |
| Same model with RMSNorm + rotary embeddings + SwiGLU (one seed, 16.9M parameters): Arabic val / unseen dialects / English | **1.95** / **2.76** / **1.49**, against 2.02 / 2.75 / 1.56 for the baseline row: lower on every trained source, not on the unseen dialects; the second seed agrees (D-029) | `reports/eval/final-modern-17m`, D-028 |

Tokens per word uses whitespace words, a rough unit for Arabic. Perplexity per token is not
comparable between tokenizers; bits per character is. Compare a split with the same split: validation
and test of one source differ by up to 0.10 bits per character, far more than the 0.01 between seeds
(D-023). The limits of each number are in the decision log.

## Quick start

```bash
make install   # uv sync + pre-commit hooks
make env       # confirm the GPU is visible
make check     # ruff + mypy + pytest (no GPU needed)
```

## The pipeline, as commands

```bash
# data: sample, analyse, measure, tokenize (data lands in data/, which git ignores)
uv run scratchllm data sources
uv run scratchllm data sample fw2_arb --n-docs 50000          # one source, with a manifest
uv run scratchllm data analyze data/raw/eda/*.manifest.json   # EDA checks -> reports/eda
uv run scratchllm data clean-report data/raw/eda/*.manifest.json
uv run scratchllm data leakage-report data/raw/eda/*.manifest.json

# tokenizer: byte-level BPE trained on the cleaned, normalized text; fertility vs other tokenizers
uv run scratchllm tokenizer train --out artifacts/tokenizer/bpe-16k.json --vocab-size 16384
uv run scratchllm tokenizer fertility artifacts/tokenizer/bpe-32k.json --sizes 16384 \
    --compare openai-community/gpt2

# token files for training, and a check that they still match their descriptions
uv run scratchllm data tokenize artifacts/tokenizer/bpe-16k.json --out-dir data/processed/tokens-16k
uv run scratchllm data verify-tokens data/processed/tokens-16k/*.tokens.json

# train (resumable), evaluate on every held-out token, generate
uv run scratchllm train configs/smoke.yaml                    # about 15 s, checks the whole path
uv run scratchllm train configs/local-17m.yaml --resume auto  # the 17.1M model on a 4 GiB GPU
uv run scratchllm eval runs/local-17m/best.pt
uv run scratchllm generate runs/local-17m/best.pt --tokenizer artifacts/tokenizer/bpe-16k.json \
    --prompt "The history of the city began when" --temperature 0.8 --top-k 40 --seed 1   # add --cache for a faster CPU run
```

A training run writes `runs/<name>/metrics.jsonl` (one JSON object per line), `last.pt` and
`best.pt`, and resumes exactly where it stopped. Every sampled source has a manifest with sha256
hashes; `data verify` and `data verify-tokens` re-check them.

## Layout

| Path | Purpose |
|------|---------|
| `src/scratchllm/data/` | Sources, seeded sampling with manifests, train/val/test split by site, cleaning rules, personal-data masking, token files |
| `src/scratchllm/eda/` | EDA checks, near-duplicate and leakage measurement, reports |
| `src/scratchllm/tokenizer/` | Normalization, pre-tokenizer, BPE trainer, `Tokenizer`, fertility report |
| `src/scratchllm/model/` | Attention, layers, GPT, generation |
| `src/scratchllm/training/` | Config, schedule, batches, trainer, checkpoints, log, evaluation |
| `src/scratchllm/finetune/` | Empty: LoRA/SFT is not built |
| `configs/` | One YAML per run (`smoke`, `pilot-17m`, `local-17m`, and the three `ablation-*` runs of D-024) |
| `scripts/` | Diagnostics on a checkpoint and on the token files, and the scripts that build the tables of a decision entry (D-023, D-024); each states how to run it |
| `tests/` | Unit tests that define each component's contract |
| `docs/` | Problem statement, decision log, data plan |
| `reports/` | Tracked reports only (`final-*`); working runs are ignored. `reports/diagnostics/final-d023/` holds the outputs of the diagnostic scripts |
| `artifacts/tokenizer/` | The trained tokenizers and their provenance |
